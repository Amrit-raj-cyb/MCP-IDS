# Benign MCP servers and simulation controls

The three benign servers produce **normal** MCP traffic, including normal
mistakes (wrong paths, SQL typos, missing pages). Benign mistakes matter: if
benign sessions never contained errors, an IDS could learn that "errors mean
attack", and it would then flag every user who mistypes a filename.

| Server | Tools | Resource (fresh per session) | Typical traffic |
|---|---|---|---|
| `filesystem` | `list_directory`, `read_file`, `write_file`, `search_files` | temp copy of `sandbox/` | small requests, small-medium text results |
| `sqlite` | `list_tables`, `describe_table`, `read_query`, `insert_row` | temp DB built from seed 1234 | SQL in requests, JSON row sets in results, SQL errors |
| `web_fetch` | `fetch(url, max_length, start_index)` | synthetic site (`testweb` container or local thread) | URLs in requests, large text results, pagination, HTTP errors |
| `calculator` | `add_numbers`, `convert_temperature`, `percentage` | none | tiny numeric calls; also the **clean twin** of the poisoned-tool attack |
| `shadowing_control` | `read_file` | none | static synthetic catalogue fixture; matched control for duplicate-name metadata |
| `sampling_control` | `request_summary` | none | static synthetic fixture; matched control that does not request sampling |
| `writing_assistant` (lab 0.9.1) | `summarize_text`, `translate_text` | none | **benign server that uses MCP sampling**: asks the client's model to write a summary or translation |
| `helpdesk` (lab 0.9.1) | `classify_ticket`, `draft_reply` | none | **benign server that uses MCP sampling**: asks the client's model to triage a ticket or draft a reply |

The shadowing and sampling controls are additional fixtures for matched
scenarios. The original filesystem, SQLite, web-fetch and calculator servers
are unchanged.

**Why benign sampling servers (lab 0.9.1).** Until lab 0.9.0 the only server that
ever sent `sampling/createMessage` was the inert sampling-injection simulation,
so "a server asked the client's model" alone meant attack. Real servers without a
model of their own do this routinely. `writing_assistant` and `helpdesk` state
their requests openly in plain instructions; the lab client answers every
sampling request with the same fixed local callback, so the reply is no giveaway
either. They are not part of the all-servers mix of other tasks (that would
change earlier scenarios), and their tasks have no attack twins.

## SQLite server
**What it is:** a synthetic shop database with `users` (30), `products` (20),
`orders` (80) and `logs` (50). People, emails (`@example.test`) and products
are invented. The DB is generated by `servers/benign/sqlite/seed_db.py`, so
it isn't committed and is identical for the same seed.

**Safety (each item is tested in `tests/test_servers.py`):**
| Risk | Control |
|---|---|
| Writes through `read_query` | read-only connection **and** an SQLite authorizer that allows only SELECT/READ/FUNCTION/RECURSIVE |
| `ATTACH DATABASE` to read other files | denied by the authorizer |
| `load_extension` and file functions | denied |
| Stacked statements (`SELECT 1; DROP ...`) | sqlite3 runs one statement per call; the rest is an error |
| Runaway queries (infinite recursive CTE) | progress handler interrupts after 2 s |
| Huge results | capped at 200 rows (`truncated: true`) |
| SQL injection via `insert_row` | table allow-list (`orders`, `logs`); column names checked against the schema; values bound with `?` |

## Web fetch server
**What it is:** a `fetch` tool like popular fetch MCP servers. HTML is turned
into plain text, and long pages come back in chunks (`start_index`).

**The test site** (`servers/benign/web_fetch/site/`) is a fictional company
("Lab Widgets"): home, about, products, docs, news and a long FAQ (~11 KB,
needs 4 chunks). In Docker it runs as the `testweb` container
(`http://testweb:8080`). Locally a thread serves it on `127.0.0.1` with a
random port.

**Safety (tested):**
| Risk | Control |
|---|---|
| Fetching the internet or internal hosts (SSRF) | exact origin allow-list (scheme + host + port) from `MCP_WEB_BASE_URL`, set by the lab and never by the agent |
| URL parser tricks (`http://a@evil@host/`, credentials) | URLs containing user/password are refused |
| Redirect to elsewhere | redirects are not followed (3xx becomes an error) |
| Proxy env vars rerouting traffic | `ProxyHandler({})` ignores them |
| Slow or huge responses | 5 s timeout, 256 KiB cap |
| Missing allow-list | server refuses to start |
| (defence in depth) | Docker lab network has no internet route |

**Reworded descriptions (opt-in).** `common/descriptions.py` holds three
alternative wordings for every filesystem, SQLite, web-fetch, writing-assistant and help-desk tool
(`MCP_DESCRIPTION_VARIANT` 1–3; 0 = original docstrings, the default). Only
servers without an attack twin vary.

**Why multi-server benign tasks matter:** the shadowing attack (Phase 7)
needs two or more servers in one session. If all benign sessions used one
server, "several servers" alone would identify attacks, and the detector would
learn nothing useful. Benign multi-server sessions close that shortcut.

## Notes for the dataset
* Generate the dataset **in Docker**. There the site URL is always
  `http://testweb:8080`; locally the port changes every run, which would add
  meaningless variation to message sizes.
* Server start-up (~2–3 s each, servers started one after another) dominates
  session duration. Don't treat raw session duration or `initialize` latency
  as behaviour features.
